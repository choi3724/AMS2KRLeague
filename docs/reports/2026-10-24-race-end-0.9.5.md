## 원인 → 최소 수정
1. 후보의 완주 시각 조건이 ‘아무 league driver의 FINISHED 존재’였다. 뒤차가 먼저 FINISHED로 관측돼도 1위 시각이 됐다.
   - HostRecorderEngine.cs: 실제 선두를 판별하고 동일 slot/generation/name의 비완주→완주 전환 관측이 있을 때만 종료 시각을 기록한다. 앞선 운전자가 사라졌다고 다음 사람을 우승자로 올리지 않는다.
   - 안전차가 순위를 점유하는 경우 판별에서만 제외한다. 원본 참가자 순위·랩·상태는 바꾸지 않는다.
2. 중도 접속 첫 화면의 FINISHED를 실제 완주 전환으로 간주했다.
   - 최초 완주 상태 관측은 별도의 내부 수집 한도에 사용한다. 정확한 전환 시각이 없으면 leaderFinishedAtUtc는 null로 유지하고 LEADER_FINISH_TIME_UNKNOWN 근거를 남긴다.
   - SessionWitnessCaptureEngine.cs: 이미 완주자가 있는 첫 관측을 전체 시작 관측으로 분류하지 않는다. 최대 수집 확정이 전체 세션 관측 증거를 새로 만들어내지 않는다.
   - 정확한 시각이 불명확하면 ‘실제 완주 후 정확히 300초’를 증명할 수 없다. 이 경우 수집만 최초 관측 후 300초로 제한하며 실제 종료 시각을 만들지 않는다.
3. 300초 확정 후 남은 Racing/NotStarted 차량이 다음 프레임에서 재시작 조건을 다시 만족했다.
   - ActivityCaptureRuntime.cs: 단순히 남아 있는 주행·미출발 상태로 재캡처하지 않는다. 새 그리드 전환, 동일한 종료 참가자의 랩 초기화, 명시적인 InGameRestarting 등 실제 새 경기 근거를 구분한다.
   - 재현: 300초 확정 직후 다음 프레임에 CurrentTelemetryIdentity가 다시 생성됐다. 수정 후 계속 null이며 실제 재시작은 새 identity를 생성한다.
4. 전송 게이트 분석 결과
   - RaceUploadCompletionGate.cs는 변경하지 않았다.
   - 정책 v2의 새 witness는 stable=false여도 실제 저장→provisional 판정→큐에 등록되고, 자체 원본 근거로 전송 가능했다. Compact의 기존 finalize ACK 보호 및 구형 대기열 보호는 유지한다.
   - 전송 본문 byte equality와 idempotency key를 실제 Cafe24ActivityUploadTransport/ActivityUploadWorker를 통과해 검사했다. HTTP는 오프라인 HttpMessageHandler이며 운영 전송이 아니다.
