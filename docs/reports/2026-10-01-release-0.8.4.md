## 사용자 보고와 원인 판단
- 증상: N 계기판만이 아니라 모든 HUD가 0.2~0.5초 간격으로 갱신되고, 그 사이에는 멈춰 보인다.
- 작업 관리자에서 CPU 우선순위를 "높음"으로 올려도 같다. 따라서 CPU 스케줄링 경쟁만으로는 설명되지 않는다.
- 0.8.1 이후 기본 경로는 WPF layered 창 + hardware 렌더링이다(`ClientStartupPolicy`: 인자가 없으면 `UseGlass=false`, `RenderMode.Default`).
  - 2026-09-25 보고서에서 이 경로의 `PresentWithGDI → ReadIntoSysMemBuffer → GetRenderTargetData` readback이 확인됐고, 고부하 HUD 전달 p95가 약 97ms였다.
  - 이 readback은 HUD를 GPU에서 그린 뒤 결과를 시스템 메모리로 다시 읽어 오는 단계다. 게임이 GPU를 모두 쓰면 게임 작업 뒤에서 기다린다.
  - HUD 창은 모두 WPF 렌더 스레드 하나를 공유한다. 그래서 창 하나가 대기하면 모든 HUD가 같이 멈춘다.
- 사용자는 GPU가 필요 없는 수준이면 CPU만 쓰는 쪽을 선호했다.
  - 2026-09-12 renderer matrix의 SoftwareOnly layered(A) 측정은 GPU 부하가 없는 조건이었다. 결과는 N 105.9Hz / p95 13.9ms / >33ms 0회, CPU 7.2%(hardware 4.8%)였다.
  - 따라서 HUD 내용 자체는 CPU만으로 60Hz를 낼 수 있다고 판단했다.
  - 단, 이 측정값은 실제 게임 GPU 부하 아래에서 잰 수치가 아니다.

## 발견했지만 고치지 않은 문제
- `UiTick` DispatcherTimer는 `Background` 우선순위다.
  - hardware 경로에서는 144Hz Monitor 시계가 Render 우선순위로 작업을 계속 넣는다. 그 결과 순위표·전후방 거리 같은 20Hz 갱신이 밀릴 수 있다.
  - 이번 CPU 기본 경로에서는 144Hz 시계를 쓰지 않으므로 영향이 줄어든다.
  - hardware·glass 경로에는 그대로 남아 있다.
- CHANGELOG에 0.8.1~0.8.3 항목이 없다. README의 0.8.0 설명은 0.8.1에서 기본 경로가 layered로 되돌아간 사실을 반영하지 않는다.
- WPF SoftwareOnly에서 `DropShadowEffect`(주행 HUD 값 텍스트)는 CPU로 블러를 처리한다. 실제 CPU 비용은 측정하지 않았다.
