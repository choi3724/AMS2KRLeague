# AMS2 리그 오버레이 데이터 기록·전송·통신 명세

작성일: 2026-09-09 · 기준: 오버레이 0.5.1 소스 `c7159dc`

이 문서는 현재 프로그램이 데이터를 어디서 읽고, 무엇을 저장하며, 언제 어떻게 서버로 전달하는지를 설명합니다. 압축 방식과 용량 절감 제안은 제외합니다. 사고 수집 범위를 확대한 작업은 원복된 상태이며, 기존 **사고 전 3초~후 3초**를 기준으로 합니다.

확인 범위는 현재 오버레이 소스와 이 PC의 Cafe24 서버 소스입니다. 운영 서버의 배포 파일·설정·DB 전체가 로컬 소스와 일치하는지, 특정 경기의 모든 자료가 실제 수신됐는지는 이번 문서 작성에서 검증하지 않았습니다. 아래 수집 주기는 코드의 목표값이며 실제 기록 간격을 보장하는 실측값이 아닙니다.

## 1. 전체 흐름

오버레이는 **게임이 제공하는 정보를 읽어 PC에 기록하고, 레이스 종료 조건이 충족되면 전송 가능한 기록들을 서버에 차례로 제출**합니다. 서버는 여러 사용자가 보낸 관측 자료를 보관하고 경기 결과와 연결합니다.

```text
AMS2 게임
 ├─ 공유 메모리: 차량·순위·랩·날씨·게임 상태
 └─ 접속 로그: 싱글/멀티 자동 판정 근거
          ↓
오버레이가 읽고 분류
 ├─ 화면 표시: 타워·이벤트·페달·속도·기어
 ├─ 개인 활동/경기 관측 기록 생성
 └─ 리플레이·사고·차량 상세·기록 품질 자료 생성
          ↓
사용자 PC에 파일 저장 + 전송 대기 목록 등록
          ↓
레이스 결과 안정화 + 마지막 기록 저장 완료 + 멀티 확인
          ↓
전송 가능한 기록을 여러 HTTPS 요청으로 제출
          ↓
웹서버가 검사 → 저장 → 경기/관측자 연결 → 응답
          ↓
PC에서 전송 완료 처리 또는 재시도 대기
```

| 용어 | 쉬운 설명 |
|---|---|
| 세션 | 연습, 예선, 레이스처럼 게임 진행이 나뉘는 단계 |
| 관측 기록 | “이 PC에서 이 시간 동안 이 참가자들과 결과를 보았다”는 자료 |
| 텔레메트리 | 시간에 따라 달라지는 위치·속도·조작·차량 상태 등의 수치 |
| 청크 | 긴 기록을 시간 구간과 데이터 종류로 나눈 파일 묶음 |
| 전송 대기열 | 아직 서버 전송이 끝나지 않은 파일들의 목록 |
| API | 프로그램이 서버에 데이터를 제출하거나 정보를 받는 접수 창구 |
| 원본 | 문맥에 따라 게임 원본, PC 저장본, 서버 수신본이 다름. 세 가지는 동일하지 않음 |

## 2. 게임 정보를 읽는 방법

### 2.1 공유 메모리

AMS2가 다른 프로그램에서 읽을 수 있도록 마련한 메모리 영역을 사용합니다. 현재 대상은 **Shared Memory v14**, 메모리 이름은 `$pcars2$`입니다. 게임의 Project CARS 2 공유 메모리 옵션이 활성화되어 있어야 합니다.

오버레이는 이 영역을 읽기 전용으로 엽니다. 이 데이터 경로는 화면의 글자를 인식하거나 게임 영상 파일을 분석하는 방식이 아닙니다. 게임이 적어 준 숫자와 상태를 읽습니다.

- 게임 정보 읽기: 약 **33.333밀리초마다**, 초당 약 30회 시도합니다.
- 읽기 전후 게임의 갱신 번호를 비교하여, 게임이 쓰는 도중의 섞인 자료인지 확인합니다.
- 한 번의 읽기에서 최대 3회 확인해도 일관된 자료를 얻지 못하면 해당 읽기는 사용하지 않고 실패 횟수를 셉니다.
- 게임 연결 상태 확인은 약 1초 간격입니다.
- 화면 갱신 타이머는 약 16밀리초입니다. 화면이 자주 바뀌어도 새 게임 데이터가 그 횟수만큼 생긴다는 뜻은 아닙니다.

### 2.2 싱글/멀티 접속 로그

모드 판정에는 `문서\Automobilista 2\log\online.log` 및 이전 로그를 읽습니다. 현재 실행 중인 AMS2의 시작 시각과 로그를 대조하고, 로비 입장·연결 완료·퇴장 메시지를 추적합니다.

| 전송 구분값 | 의미 | 현재 결과/청크 전송 정책 |
|---|---|---|
| `MULTIPLAYER` | 해당 관측 구간이 멀티플레이로 확인됨 | 다른 전송 조건도 통과하면 전송 |
| `SINGLE_PLAYER` | 싱글플레이로 판정됨 | 전송하지 않음 |
| `UNKNOWN` | 로그를 읽지 못했거나 구간을 확실히 판정하지 못함 | 전송하지 않음 |

참가자가 여러 명이라는 이유만으로 멀티플레이로 판정하지 않습니다. AI가 있는 싱글플레이도 있기 때문입니다. 비공개 방 여부 역시 싱글/멀티 구분과 별개입니다.

판정 결과가 15초 넘게 갱신되지 않거나, 멀티 접속을 확인하는 로그가 오래된 경우 `UNKNOWN`으로 돌아갈 수 있습니다. 전송 전에는 관측 시작부터 끝까지 같은 모드였는지 확인하며, 관측 종료 시각이 현재보다 최소 10초 이전이어야 합니다.

**수집 가능 여부와 전송 가능 여부는 별도입니다.** 싱글 또는 미확인 구간도 수집 조건을 충족하면 PC에 기록될 수 있지만, 현재 전송 조건에서는 서버로 보내지 않습니다.

## 3. 어떤 데이터를 기록하는가

값은 게임에서 실제로 관측할 수 있을 때만 들어갑니다. 상대 차량에 대해 알 수 있는 정보와 현재 관전/운전 중인 차량의 상세 정보는 범위가 다릅니다.

| 자료 종류 | 주요 내용 | PC 보관 | 현재 서버 전송 |
|---|---|---|---|
| 개인 활동 기록 | 본인으로 식별한 참가자의 차량·트랙·시작/종료 시각·레이스 결과 또는 타임어택 랩 | 예 | 지원 형식·식별·멀티·레이스 종료 조건 충족 시 |
| 경기 관측 기록 | 참가자 명단, 예선 순위, 출발 그리드, 최종 결과, 관측 구간, 이벤트, 날씨, 신뢰도 | 예 | 멀티 및 레이스 종료 조건 충족 시 |
| 세션 정보 | 트랙·레이아웃·길이, 게임/클라이언트 버전, 세션 종류, 참가자 사전, 날씨, 수집 가능 항목 | 예 | 공개 자료로 전송 조건 충족 시 |
| 경기 이벤트 | 순위 변화, 랩 및 세션 변화, 피트·깃발·결과 상태 변화, 사고 후보 | 예 | 공개 자료로 전송 조건 충족 시 |
| 참가자 리플레이 | 차량별 시간·위치·진행거리·순위·상태 및 일부 랩 정보 | 예 | 공개 자료로 전송 조건 충족 시 |
| 트랙 경로 보조 자료 | 실제 관측한 차량의 위치를 트랙 진행거리별로 모은 좌표 | 예 | 리플레이 보조 자료로 전송 조건 충족 시 |
| 사고 구간 | 사고 후보 전후의 관련 차량 위치·상태·충돌 관측값 | 예 | 공개 자료로 전송 조건 충족 시 |
| 운전자 상세 텔레메트리 | 페달·조향·기어·RPM·가속도·연료·손상·타이어 등 | 예 | **현재 차단: 로컬 보관** |
| 기록 품질·마감 자료 | 누락·처리 실패 집계, 기록 마감 요청과 저장 완료 확인 | 예 | 공개 자료로 전송 조건 충족 시 |

여기서 “공개 자료”는 프로그램 내부의 자료 분류입니다. 모든 수신 파일을 즉시 인터넷에 공개한다는 의미가 아닙니다.

### 3.1 경기 관측 기록에 포함되는 결과

예선·그리드·레이스 결과의 참가자 행에는 다음 종류의 내용이 들어갑니다.

- 참가자 자리 번호와 해당 자리의 교체 이력 번호, 이름, 차량, 클래스
- 순위, 완료 랩 수, 현재 랩/섹터, 마지막 랩과 최고 랩 시간
- 완주·리타이어·실격 등 게임이 제공한 결과 상태와 피트 상태
- 처음/마지막 관측 시각, 참가자 활성 상태와 사라짐 여부

관측 기록에는 이를 만든 PC의 식별자, 수집 시작·종료 시각, 중도 참가 여부, 관측 품질, 누락/문제 목록도 함께 들어갑니다. 예선이나 그리드를 보지 못한 PC는 그 자료가 없을 수 있습니다.

게임이 확정 제공하지 않는 공식 총 경기 시간이나 공식 최종 갭을 임의로 만들어 넣지 않습니다. 원자료의 전체 참가자 목록에는 Safety Car가 포함될 수 있으며, 리그 순위의 참가자 분모와 종료 판정에서는 Safety Car를 제외하는 별도 분류를 사용합니다.

### 3.2 개인 상세 텔레메트리

현재 운전/관전 대상 차량에서 노출되는 값이 대상입니다.

| 분야 | 기록 대상의 예 |
|---|---|
| 조작 | 악셀, 브레이크, 클러치, 핸드브레이크, 조향, 게임 보정 전 입력, 기어 |
| 움직임 | 위치, 속도, 방향, 회전수, 속도 벡터, 가속도, 회전 운동 |
| 엔진/연료 | 연료량, 탱크 용량, 오일·냉각수 온도와 압력, 엔진 토크, 부스트 |
| 차량 상태 | 엔진·공력·서스펜션 손상, 브레이크 배분, 충돌 상태 |
| 타이어/바퀴 | 각 바퀴의 온도·압력·마모·컴파운드·노면 종류·회전·서스펜션·차고 |
| 보조 장치 | ABS, TC, DRS, ERS, 런치 및 클러치 관련 상태 |
| 주행 맥락 | 랩·섹터·유효 랩 여부, 피트, 깃발, 날씨 |

이 목록은 게임에서 매번 모든 값이 제공된다는 보장이 아닙니다. 특히 공유 메모리의 관전 대상 차량이 인증된 사용자 본인의 차량이라는 확실한 증명이 없으므로, 현재 프로그램은 이 자료를 `PRIVATE_DRIVER_ANALYTICS`로 보관하고 서버로 보내지 않습니다. 로컬 서버 소스도 해당 업로드를 거부합니다. **오버레이의 페달 그래프가 움직이는 것과 페달 기록의 서버 전송은 별개입니다.**

## 4. 얼마나 자주 기록하는가

게임을 읽은 뒤 저장용 변환은 50밀리초 단위의 수집 제한을 거칩니다. 이후 자료 종류별로 기록 빈도를 달리합니다. 약 30Hz의 게임 읽기, 20Hz 수집 제한, PC 처리 지연이 함께 작용하므로 아래는 목표 간격입니다.

| 자료/항목 | 현재 목표 기록 정책 |
|---|---|
| 세션 정보 | 시작·종료, 구조/날씨의 주요 변화, 약 60초 간격 확인 |
| 경기 관측의 날씨 이력 | 약 60초 간격 |
| 경기 이벤트 | 해당 변화가 관측됐을 때 |
| 리플레이 중간 수집 | 약 200밀리초, 초당 5회 |
| 최종 리플레이의 기본 진행/순위 상태 | 약 2초 간격 + 관측된 순위·피트 변화 |
| 최종 리플레이의 공간 좌표·방향·속도 | 약 500밀리초 간격 |
| 인접 순위 차량 간 근접 경쟁의 진행 정보 | 약 500밀리초 간격으로 추가 선택 |
| 수집 시작 후 첫 10초의 리플레이 진행/좌표 | 중간 수집 주기인 약 200밀리초 간격 |
| 리플레이의 부가 정보 | 약 20초 간격: 섹터 시간, 최고/최근 랩, 일부 상세 상태 등 |
| 사고 구간 | 약 50밀리초, 초당 최대 목표 20회 |
| 운전자 빠른 입력/주행 수치 | 약 50밀리초: 악셀·브레이크·조향·속도·진행거리·일부 가속도 |
| 운전자 위치/방향/RPM | 약 200밀리초 |
| 운전자 연료/일부 손상/노면 온도 | 약 1초 |
| 운전자 기어·클러치·핸드브레이크·각종 상태 | 입력 수집 시 확인하고 값이 바뀔 때 기록 |
| 나머지 운전자 상세 수치 | 약 20초 간격 |

연습과 예선도 현재 같은 리플레이 기본 옵션을 사용합니다. “레이스 좌표만 500밀리초, 예선은 5초” 같은 과거 제안은 현재 적용 상태로 취급하지 않습니다.

### 4.1 전부 기록한다는 말의 정확한 범위

현재 프로그램은 **게임이 내보내는 모든 순간의 원본을 그대로 파일에 복제하는 방식이 아닙니다.** 위의 주기에 따라 값을 선택하고, 항목별로 정해진 숫자 단위로 변환합니다.

예를 들어 최종 리플레이 좌표는 0.1m 단위, 사고 좌표는 0.01m 단위입니다. 빠른 운전자 악셀/브레이크는 0~255 단계로 저장됩니다. 게임 원본의 소수점 아래 숫자까지 무한히 보존하는 구조는 아닙니다.

화면 그래프의 부드러운 표현이나 웹 리플레이의 중간 움직임은 저장 샘플 수와 같지 않습니다. 화면에서 두 점 사이를 부드럽게 연결해도 그 사이의 실제 관측 기록이 새로 생기지는 않습니다.

## 5. 사고 기록의 현재 범위

사고 기록은 상시 모든 차량의 고빈도 영상을 저장하는 방식이 아니라 **사고 후보가 관측됐을 때 관련 구간의 수치를 남기는 방식**입니다.

1. 최근 약 10초의 사고용 프레임을 메모리에 임시 보관합니다.
2. 충돌 또는 이상 상황 후보가 생기면 해당 시점 전 3초를 꺼냅니다.
3. 이후 3초 동안 관련 참가자의 수치를 추가합니다.
4. 사고 후보 번호·발생 이유와 함께 저장합니다.

| 사고 후보 신호 | 해석 |
|---|---|
| 충돌 상대/충돌 강도 변화 | 관전 대상 차량에서 충돌 변화가 관측됨 |
| 충돌 상태 변화 | 게임의 사고 상태 코드가 달라짐 |
| 갑작스러운 결과 상태 변화 | 완주/리타이어 등의 종료 상태로 전환됨 |
| 참가자 사라짐 | 이전에 보이던 참가자가 사라짐 |
| 급격한 공간 위치 변화 | 좌표가 크게 변함 |
| 빠른 접근과 매우 가까운 거리 | 충돌 가능성을 검토할 구간 |

후보는 확정 사고나 과실 판정이 아닙니다. 정상 종료, 접속 종료, 위치 갱신 문제도 후보 신호에 들어갈 수 있습니다.

- 같은 종류·같은 관련자 조합의 후보에는 2초 재생성 제한이 있습니다.
- 관련 참가자는 최대 8명입니다. 관련 차량 주변 50m 안에서 최대 4명을 추가하되 전체 8명 한도를 지킵니다.
- 동시에 유지하는 사고 구간은 최대 4개입니다.
- 수집을 늦게 시작했거나 일찍 종료하면 전후 3초가 모두 채워지지 않을 수 있습니다. 한도나 처리 문제도 기록 누락의 원인이 될 수 있습니다.
- 상세 충돌 상대·강도는 관전 대상 차량에서 얻는 값입니다. 이를 모든 상대 차량의 직접 충돌 센서 값처럼 해석하면 안 됩니다.

트랙 경로 보조 자료는 차량 관측 좌표를 진행거리 약 20m 구간별로 모읍니다. **실제 도로의 좌우 경계, 도로 폭, 공식 중앙선 좌표를 수집하는 기능은 아닙니다.** 차량이 달린 경로를 바탕으로 하므로 경로가 도로 한가운데라는 보장도 없습니다.

## 6. PC에 저장하는 방법

기본 저장 위치는 다음과 같습니다.

```text
%LOCALAPPDATA%\AMS2KRLeague\activity\
 ├─ activities\       개인 활동 기록과 파일 명세
 ├─ witness\sessions\ 경기 관측 요약, 원천 증거, 전송용 기록
 ├─ future-telemetry\ 리플레이·사고·운전자 상세·세션 자료
 │    └─ attempt-ledgers\ 기록 시도별 누락/마감 장부
 └─ upload-queue\items\ 결과·관측 기록의 전송 대기 목록
```

현재 실행 경로에서는 긴 텔레메트리를 **5분 단위 시간 구간**으로 묶도록 설정합니다. 공용 옵션 클래스의 기본값은 30초이지만 실제 앱이 300초로 덮어씁니다. 종료 시에는 5분을 채우지 않은 마지막 구간도 마감합니다.

5분당 파일 하나라는 뜻은 아닙니다. 같은 시간 구간에서도 리플레이·사고·개인 상세·세션 자료가 분리되고, 개인 상세 자료 역시 여러 종류로 나뉩니다.

| 파일 역할 | 들어가는 내용 |
|---|---|
| 자료 본문 | 실제 경기/관측/시간별 수치 |
| 명세 파일 | 자료 식별자, 시간 범위, 종류, 본문 검사값, 버전 |
| 전송 상태 파일 | 대기/완료/재시도 여부, 시도 횟수, 다음 시도 시각, 서버 응답 |
| 누락 장부 | 수집·변환·저장 단계에서 파악한 누락과 마감 상태 |

결과 전송 대기 항목에는 `payload.json`, `metadata.json`, `state.json`이 따로 있습니다. 텔레메트리는 자료 파일 옆의 `*.upload.json`에 전송 정보를 둡니다.

파일은 임시 경로에 먼저 쓴 뒤 확정 위치로 옮기는 방식을 사용합니다. 정상 전송 후에는 상태를 완료로 바꾸며, 확인한 전송 경로에서는 성공 즉시 원본을 지우지 않습니다. 따라서 **PC 저장 용량과 서버 전송량은 같지 않습니다.**

아직 파일로 확정되지 않은 메모리 내 구간까지 강제 종료·전원 차단에서 모두 보존된다고 보장할 수는 없습니다. 전송 재시도는 이미 저장된 파일에 대한 보호 기능입니다.

수집 단계에는 메모리가 끝없이 늘어나지 않도록 제한이 있습니다. 주요 기본 한도는 프레임당 참가자 64명, 입력 대기 통로 512개, 관측 기록의 타임라인 이벤트 4,096개입니다. 처리 지연이나 한도 초과 시 누락될 수 있으며, 텔레메트리는 파악한 누락을 별도 장부에 집계합니다. “모든 필드를 지원한다”는 것과 “실행 중 모든 샘플이 빠짐없이 저장된다”는 것은 같은 보장이 아닙니다.

## 7. 전송은 언제 시작되는가

현재 일반 전송 경로는 다음 조건을 모두 확인합니다.

1. 관측 중인 리그 참가자들의 결과 상태가 모두 종료 상태에 도달했습니다.
2. 결과를 비교하는 핵심 항목이 약 **1.5초 이상 안정적으로 유지**됐습니다.
3. 최종 텔레메트리와 기록 품질/마감 자료의 로컬 저장이 완료됐습니다.
4. 안정된 레이스 결과를 포함한 관측 기록이 로컬 전송 대기열에 있습니다.
5. 해당 자료의 관측 구간이 멀티플레이로 확인됐습니다.
6. 관측 구간 종료 후 최소 10초가 지났고, 해당 자료가 공개 전송 대상입니다.

이 조건이 충족되면 같은 수집 세션에 묶인 연습·예선·레이스 자료를 전송 대상으로 풉니다. **개인의 결승선 통과나 게임 프로세스 종료만으로 전체 경기 전송을 시작하는 방식은 아닙니다.**

| 상황 | 현재 처리 |
|---|---|
| 연습 → 예선 → 레이스까지 이어지고 결과가 확정됨 | 같은 수집 세션의 전송 가능 자료를 종료 후 순차 전송 |
| 연습 또는 예선만 하고 나감 | 안정된 레이스 결과가 없으면 현재 전송 관문을 통과하지 못함 |
| 본인이 먼저 완주/리타이어함 | 관측 결과의 다른 리그 참가자 종료 상태까지 확인 |
| 결과 확정 전 게임/오버레이를 종료함 | 저장 마감을 시도하나, 안정된 레이스 결과가 없으면 전송 보류 |
| 결과 저장 뒤 인터넷 연결이 끊김 | 이미 저장한 전송 가능 자료를 재시도 대기 |
| 싱글 또는 모드 미확인 | 로컬 자료가 있어도 전송하지 않음 |
| 관측 시작 시 참가자가 1명뿐임 | 관측 기록 시작 조건인 2명 이상을 충족하지 못할 수 있음. 레이스 종료 관문에도 영향 |

트랙 변경, 수집 범위 이탈, 재시작으로 기록 묶음이 나뉠 수 있습니다. “연습·예선·레이스를 모아서 전송”은 **같은 수집 세션으로 연결된 범위**에 적용되며, PC에 있는 모든 과거 연습 파일을 다음 레이스와 무조건 합치는 방식은 아닙니다.

## 8. 늦게 참가한 사용자의 기록

늦게 오버레이를 켜거나 세션에 들어오면 그 시점부터 관측합니다. 들어오기 전의 주행 기록을 만들어 채우지 않습니다.

| 항목 | 의미 |
|---|---|
| 관측 시작/종료 시각 | 이 PC가 실제 자료를 모은 범위 |
| 추정 세션 시작 시각 | 서버가 같은 경기를 묶는 데 사용하는 보조 정보 |
| `FULL_SESSION` | 코드의 완전성 판정에서 전체 세션 관측으로 분류 |
| `MID_SESSION` | 세션 중간부터 관측한 자료 |
| `END_ONLY` | 결과 부근만 관측한 자료 |
| `UNKNOWN` | 관측 범위 분류가 불확실함 |

예를 들어 A가 23:40부터, B가 00:10부터 관측했더라도 둘 다 종료 결과를 계속 관측하면 같은 경기의 끝을 기준으로 자료를 마감할 수 있습니다. 다만 PC별 읽기 시점이 달라 **종료 시각이 밀리초까지 동일하다고 보장하지는 않습니다.** 목표는 같은 종료 상태를 관측하는 것입니다.

각 PC에는 별도의 관측자/기록 시도 번호가 있고, 같은 경기의 자료를 묶는 비교값도 있습니다. 서버는 비교값, 추정 시각, 참가자 및 결과 증거를 이용합니다. 한 사용자의 짧은 기록만으로 다른 사용자가 관측하지 못한 구간까지 있었다고 판단하지 않습니다.

시간은 두 종류를 함께 사용합니다. `capturedAtUtc` 같은 UTC 시각은 다른 PC·서버 자료를 대조하는 데 쓰고, `sessionElapsedMs`는 해당 PC의 수집 시작 후 흐른 시간을 나타냅니다. 후자는 거꾸로 가지 않는 전용 경과 시간계로 계산하며, 매 랩마다 초기화되는 랩타임을 전체 기록 시간으로 사용하지 않습니다. 서로 다른 PC의 경과 시간 0은 같은 실제 시각이라고 볼 수 없고, PC 시계가 잘못 맞춰진 경우 UTC 대조에도 영향을 줄 수 있습니다.

## 9. 데이터를 어떤 형식으로 보내는가

### 9.1 읽을 수 있는 항목표: JSON

개인 활동과 경기 관측 기록은 항목 이름과 값으로 구성된 JSON을 사용합니다. 텍스트 형태의 전자 서식이라고 생각하면 됩니다.

| 계약 이름 | 주요 상위 항목 |
|---|---|
| `ams2-player-activity-v2` | 활동 번호, 종류, 관측 이름, 트랙/차량, 모드, 시작/종료 시각, 설정/관측 조건, 개인 결과 또는 랩 |
| `ams2-session-witness-v1` | 관측 번호, 수집 세션/시도 번호, 참가자 명단, 모드, 관측 범위/품질, 예선·그리드·결과, 이벤트, 날씨 |
| 기존 세션 정보 호환 기록 | 텔레메트리 묶음 안의 트랙/문자열/수집 가능 상태 등 낮은 빈도의 정보 |

설명용 발췌 예시이며, 그대로 제출할 수 있는 완전한 요청은 아닙니다.

```json
{
  "schema": "ams2-session-witness-v1",
  "raceMode": "MULTIPLAYER",
  "captureSessionId": "capture-example",
  "witnessId": "witness-example",
  "attemptId": "attempt-example",
  "attemptNumber": 1,
  "captureStartedAtUtc": "2026-09-08T14:40:00Z",
  "captureEndedAtUtc": "2026-09-08T15:50:00Z",
  "captureCompleteness": "MID_SESSION",
  "session": {
    "track": "Example Circuit",
    "closingReason": "RACE_RESULTS_READY",
    "raceResult": { "stable": true }
  }
}
```

`Z`는 UTC 시간을 뜻합니다. 한국 시각은 여기에 9시간을 더합니다. 위 예시의 종료는 한국 시각 9월 9일 00:50입니다.

### 9.2 숫자 중심의 정해진 서식: A2CT

빈도가 높은 리플레이·사고·상세 수치는 `AMS2_COMPACT_TELEMETRY` 버전 1, 즉 **A2CT**라는 바이너리 서식을 사용합니다. 사람이 메모장으로 읽기보다는 프로그램이 약속된 순서로 숫자를 해석하는 형태입니다.

본문 앞부분에는 형식 버전, 자료 종류, 수집 세션/시도 번호, 묶음 순번 등이 있습니다. 참가자 이름이나 반복 문자열은 번호표에 한 번 적고 숫자 번호로 참조합니다. 값이 없다는 상태도 별도로 표현합니다. 숫자 표현에는 이전 값과의 차이나 같은 값의 반복 횟수를 쓰는 규칙이 있습니다. 이것은 현재 데이터 서식의 설명이며 이번에 새로 제안한 변경이 아닙니다.

| 형식 번호 | 자료 | 주요 수치 |
|---|---|---|
| `0x0001` | 세션 고정 정보 | 트랙 길이, 최대 RPM |
| `0x0002` | 세션 변경 값 | 항목 번호와 값. 정의는 있으나 현재 주요 문자/상태 자료는 호환 JSON 경로 사용 |
| `0x0010` | 경기 이벤트 | 종류/근거/참가자 참조, 발생 시점, 위치, 이전·이후 순위, 랩/상태 코드 |
| `0x0020` | 참가자 리플레이 | 참가자/자리/교체 이력, 랩, 거리, 순위, 좌표, 방향, 속도, 랩/피트/깃발 상태 |
| `0x0021` | 트랙 경로 보조 | 진행거리와 관측 X/Y/Z 좌표 |
| `0x0030` | 운전자 빠른 수치 | 악셀·브레이크·조향·속도·거리·종/횡 가속도. 로컬 전용 |
| `0x0031` | 운전자 움직임 | X/Y/Z·방향·RPM. 로컬 전용 |
| `0x0032` | 운전자 느린 수치 | 연료·엔진/공력 손상·노면 온도. 로컬 전용 |
| `0x0033` | 운전자 변경/기타 | 항목 번호와 값. 로컬 전용 |
| `0x0040` | 사고 구간 | 사고 상대 시각, 후보/참가자 참조, 좌표·속도·상태·충돌 관측값 |
| `0x0050` | 누락 장부 | 누락 출처·횟수·관련 자료 종류 |
| `0x0051` | 기록 마감 | 접수한 작업 수, 저장 확인 작업 수, 알려진 누락 수, 완전성 코드 |

같은 시각·같은 참가자의 리플레이 진행 정보와 좌표 정보는 하나의 행으로 합칩니다. 원본 전체 공유 메모리 블록이나 `.rpl` 게임 리플레이 파일, 화면 녹화 영상을 보내는 방식이 아닙니다.

## 10. 서버와 통신하는 방법

### 10.1 연결 방식과 접수 주소

일반 데이터 업로드는 **HTTPS 요청/응답 방식**입니다. PC가 먼저 요청하고 서버가 처리 결과를 돌려줍니다. 수집한 수치를 실시간 UDP 방송이나 지속 연결된 WebSocket으로 보내는 경로는 현재 업로드 코드에 없습니다.

기본 서버 주소는 `https://krams2.mycafe24.com/ams2`입니다. 실제 요청은 아래와 같이 보냅니다.

```text
https://krams2.mycafe24.com/ams2/api.php?route=v1/session/witness
```

| 방식 | 접수 경로 | 목적 |
|---|---|---|
| POST | `v1/player/enroll` | 설치 프로그램 식별자를 등록하고 업로드용 인증표를 받음 |
| GET | `v1/bootstrap` | 현재 경기 일정 힌트와 서버 시각/버전 확인 |
| GET | `v1/health` | 상태 확인 경로에서 서버 작동 여부 확인 |
| POST | `v1/player/activities` | 개인 활동/결과 제출 |
| POST | `v1/session/witness` | 경기 관측 기록 제출 |
| POST | `v1/telemetry/chunks` | 세션·이벤트·리플레이·사고·품질/마감 묶음 제출 |

서버에는 출석 알림이나 별도 운영용 결과 접수 창구도 존재하지만, 현재 일반 오버레이 전송 경로가 그것들을 호출하는 것은 아닙니다. 특히 운영자 전용 `v1/recorder/results` 권한으로 일반 플레이어가 공식 결과를 직접 제출하는 구조가 아닙니다.

프로그램 시작 시 일정 정보를 요청하므로, **레이스 종료 전에는 인터넷 통신이 전혀 없다는 뜻은 아닙니다.** 종료 후로 제한되는 것은 위의 경기 자료 업로드입니다.

### 10.2 인증과 전송 봉투

설치 시 생성한 식별자와 클라이언트 버전으로 자동 등록하고, 서버가 발급한 인증표를 이후 업로드에 붙입니다. 실제 비밀 값은 문서에 포함하지 않습니다. 인증표는 Windows 사용자 보호 저장소를 통해 보관합니다.

| 전송 정보 | 쉬운 설명 |
|---|---|
| `Authorization: Bearer …` | 서버가 발급한 업로드용 인증표 |
| `X-AMS2-Authorization` | Cafe24 환경에서 표준 인증 헤더가 제거되는 경우를 위한 호환 전달 항목 |
| `Idempotency-Key` | 같은 자료를 다시 보내도 중복 등록하지 않도록 하는 제출 번호 |
| `Content-Type` | JSON인지 A2CT인지 알려 주는 자료 형식 |
| `X-AMS2-Chunk-Id` | 텔레메트리 묶음 번호 |
| `X-AMS2-Payload-SHA256` | 본문이 같은 내용인지 검사하는 값 |
| `X-AMS2-Session-*`, `Witness-Id`, `Attempt-*` | 어느 수집 세션·관측자·시도의 자료인지 연결하는 번호 |
| `X-AMS2-Captured-At-Start/End` | 이 묶음의 실제 관측 시간 범위 |
| `X-AMS2-Race-Mode` | 텔레메트리의 싱글/멀티/미확인 구분 |
| `X-AMS2-Visibility` | 공개 리플레이 자료인지 개인 분석 자료인지의 분류 |

JSON 결과/관측 기록은 `raceMode`를 본문에 담고, 텔레메트리 요청은 위의 모드 헤더로 전달합니다. A2CT는 서식 번호와 클라이언트 버전도 추가 헤더로 전달합니다.

HTTPS 인증서와 서버 이름은 운영체제의 표준 검증을 사용합니다. 데이터 업로드는 자동 주소 이동을 따르지 않도록 구성되어 있습니다. 기본 요청 제한 시간은 15초이며 설정 허용 범위는 1~120초입니다.

### 10.3 “한 번에 전송”의 실제 의미

현재는 **전송 시작 시점을 레이스 종료 후로 모으고, 자료는 여러 개의 요청으로 순차 제출**합니다. 하나의 거대한 파일이나 한 번의 서버 거래로 전체 경기를 등록하지 않습니다.

- 전송 반복 1회에서 결과/관측 기록은 최대 8개, 텔레메트리 청크는 최대 4개를 처리합니다.
- 결과/관측 기록을 먼저 처리하고 텔레메트리를 이어 처리합니다.
- 각 요청은 차례로 응답을 기다립니다. 일괄 병렬 전송이 아닙니다.
- 이 처리가 끝난 후 5초를 기다렸다가 다음 대기 자료를 확인합니다. 요청 처리 시간까지 포함되므로 정확히 5초마다 모든 요청이 시작되는 것은 아닙니다.
- 이 대기열에서 서로 다른 과거 경기의 전송 가능 파일도 처리할 수 있습니다.

따라서 웹사이트에 결과가 먼저 보이고 리플레이/사고/마감 자료는 조금 뒤에 도착할 수 있습니다. 한 항목의 전송 성공은 경기 전체 자료의 전송 완료를 의미하지 않습니다.

## 11. 전송 성공·실패·중복 처리

| 상태 | 의미 | 다음 처리 |
|---|---|---|
| `PENDING` | 대기 중. 전송 조건이 아직 안 맞을 수도 있음 | 조건을 다시 확인 |
| `SENT` | 서버의 저장 또는 기존 저장 자료 확인 응답을 받음 | 정상 반복 전송 대상에서 제외 |
| `FAILED_RETRYABLE` | 네트워크·일시적 서버 문제 등 | 정해진 시간이 지나면 재시도 |
| `CONFLICT` | 같은 제출 번호에 다른 내용이 연결되는 등의 충돌 | 자동 덮어쓰기 없이 보관 |
| `QUARANTINED` | 자료 형식·검사값·권한 등 비재시도 문제 | 자동 전송에서 제외하고 보관 |
| `LOCAL_PENDING_OWNER` | 개인 상세 자료의 소유자 증명이 없음 | 로컬 보관 |

개인 활동/관측 기록의 일반 재시도 대상은 네트워크 실패 및 HTTP 408·425·429·5xx입니다. 텔레메트리는 여기에 401·404·405도 재시도 대상으로 둡니다. 403 같은 권한 거부를 무조건 계속 재시도하는 방식은 아닙니다.

재시도 대기는 대략 5초 → 10초 → 20초처럼 늘어나며 최대 15분입니다. 개인 활동/관측 기록에는 ±20%의 시간 분산이 적용됩니다. 네트워크가 복구돼도 다음 재시도 시각까지 기다릴 수 있습니다.

자료를 보내기 전에 저장 당시의 검사값과 파일 내용을 비교합니다. 텔레메트리는 서버 응답의 묶음 번호와 본문 검사값도 비교합니다. 서버는 같은 제출 번호와 같은 내용이 다시 들어오면 중복 자료로 처리하고, 내용이 다르면 충돌로 처리합니다. 서버가 이미 받았는데 PC가 응답을 못 받은 상황에서도 중복 등록을 막기 위한 구조입니다.

“대기 중”은 인터넷 장애만 뜻하지 않습니다. **레이스 종료 증거 없음, 모드 미확인, 개인 자료 차단, 재시도 시각 미도래**도 구분해서 확인해야 합니다.

## 12. 종료 사실과 기록 완전성을 전달하는 방법

현재 데이터 경로에는 게임 프로세스 종료만을 전송하는 별도의 전용 API가 없습니다. 경기 종료와 기록 종료는 자료 안에 포함됩니다.

| 전달 위치 | 무엇을 알리는가 |
|---|---|
| 관측 기록의 `session.raceResult.stable` | 관측한 레이스 결과가 안정화됐는지 |
| `closingReason`, `attemptStatus`, 관측 종료 시각 | 이 관측을 언제 어떤 상태에서 닫았는지 |
| 세션 정보의 `captureEnded` | 해당 수집 범위를 마감했다는 사실 |
| `LOSS_LEDGER_V1` | 프로그램이 파악한 누락/실패 집계 |
| `ATTEMPT_FINALIZE_V1` | 기록 시도의 최종 저장 확인과 완전성 집계 |

기록 마감 파일은 일반 자료와 누락 장부를 로컬에 확정한 뒤 생성합니다. 다만 서버 제출은 여러 요청으로 나뉘므로 **결과를 받았다는 사실과 최종 마감 자료까지 받았다는 사실은 구별**해야 합니다.

이 때문에 결과가 존재하면서도 웹사이트에 “종료 무결성 기록 미확인”이 표시되는 상태가 구조적으로 가능할 수 있습니다. 그렇다고 특정 경고의 원인이 반드시 오버레이 미전송이라고 확정되는 것은 아닙니다. 해당 묶음의 전송 상태, 서버 보관 여부, 경기와의 연결, 조회 처리까지 대조해야 합니다.

## 13. 서버가 받은 뒤 하는 일

로컬 Cafe24 서버 소스에서 확인한 흐름입니다.

1. HTTPS, 요청 크기, 인증표와 권한을 확인합니다.
2. 서식 버전, 필수 항목, 식별자, 시간 범위, 데이터 내용과 검사값을 검사합니다.
3. 제출 번호와 본문 검사값으로 중복/충돌 여부를 확인합니다.
4. 관측 원자료와 조회용 항목을 저장합니다. A2CT 원자료는 A2CT 형태로 보존하고 조회에 필요한 색인 정보를 별도로 관리합니다.
5. 관측자 자료와 텔레메트리를 설치 식별자·관측 번호·세션 정보 등으로 연결합니다.
6. 같은 경기로 판단한 여러 관측 자료를 묶고 결과 일치/차이를 대조합니다.
7. 저장 여부, 중복 여부, 자료 번호와 처리 상태를 PC에 응답합니다.

관측 자료의 최초 저장 응답에는 미분류·승인 대기 상태가 포함될 수 있습니다. 텔레메트리의 보관 상태도 `ARCHIVED_NOT_PUBLISHED`로 관리합니다. 이는 자료 수신과 경기 승인·공개·리그 분류가 서로 다른 단계임을 뜻합니다.

일반 오버레이는 “이것은 공식 리그 결과다”라고 결정할 권한이 없습니다. 경기 일정 힌트를 보낼 수 있지만, 최종 경기 연결과 리그 분류·승인은 서버 측 책임입니다.
