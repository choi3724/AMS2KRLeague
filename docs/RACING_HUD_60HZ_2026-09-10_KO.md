## 화면 갱신과 서버 기록 분리
화면을 빠르게 갱신하기 위해 서버 전송용 원본 수집을 늘리지 않았습니다.

| 경로 | 주기·역할 |
|---|---|
| 기존 전체 공유 메모리 읽기 | 기존 30Hz 유지. 참가자·세션·기록 엔진에 전달 |
| 순위·이벤트·세션 계산 | 기존 최대 20Hz 유지 |
| 운전 HUD 전용 읽기 | 새 최대 60Hz. 속도·기어·RPM·페달·핸들·ABS만 읽음 |
| 화면 애니메이션 | 목표 144Hz. 그래프 이동·회전·변속 효과를 데이터 주기와 분리 |
| 로컬 기록·업로드 | 기존 코드·주기·파일 형식·멀티플레이 업로드 조건 유지 |

빠른 읽기는 기존 메모리 매핑을 읽기 전용으로 사용합니다. 전체 읽기가 사용 중이면 기다리지 않고 해당 화면 틱을 건너뜁니다. 버전·참가자·세션·시퀀스 일관성을 확인하며, 오래되거나 다른 차량의 값을 표시하지 않도록 제한했습니다. 표시용 10초 이력은 60Hz를 수용하도록 최대 1,024개로 늘렸습니다. 이 큐는 서버로 보내는 기록 큐가 아닙니다.

기존 30Hz 타이머와 `ActivityCaptureRuntime.Observe` 호출 경로는 유지했습니다. 결과·리플레이·Compact·gzip 계약은 변경하지 않았습니다. 실시간 측정 시각의 자연스러운 차이까지 동일 바이트로 보장한다는 뜻은 아니며, 표시 샘플을 기록/전송에 추가하지 않는 구조입니다.

## 60fps 목표의 남은 확인
- 실제 주행 중 `PERFORMANCE` 로그의 `drivingHz`, `shmHz`, `uiHz`와 화면 프레임을 함께 측정해야 합니다. 목표는 화면 데이터 약 60Hz, 애니메이션 60fps 이상입니다.
- 현재 모니터 테스트 결과에는 여유가 있지만, 모든 PC와 게임 부하에서 항상 60fps가 나온다고 보장할 수는 없습니다.
- 기존 VR 경로는 **15fps 제한**입니다. WPF 화면을 CPU 비트맵으로 합성·복사한 다음 GPU 텍스처로 보내므로, 수치 제한만 60으로 바꾸는 방식은 적절하지 않습니다. 이전 합성 측정도 1280×720에서 약 18ms였습니다.
- VR 60fps를 추진하려면 CPU 전체 화면 복사를 줄이고 GPU에서 직접 그린 텍스처를 공유하는 경로를 우선 검토해야 합니다. 헤드셋에서의 합성·알파·프레임 동기 검증이 필요합니다. 앞서 보류한 VR 깜빡임/출력 경로는 이번에 추가 변경하지 않았습니다.
